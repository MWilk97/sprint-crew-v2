# API contracts

Contracts for a future web console in a separate off-GX repo (see [archive/HISTORY.md](../archive/HISTORY.md)): the UI talks only to this FastAPI backend, never to the vLLM lanes, so these files are the entire integration surface.

**Pass these two files to the front-end repo:**

1. [chat-console.openapi.yaml](chat-console.openapi.yaml) — regenerate / update the typed client from this
2. [chat-console-api.md](chat-console-api.md) — human flow + JSON examples + M0 delta below

Reference timeline shape (sprint session poll): [../examples/session-timeline.json](../examples/session-timeline.json).

## Current (live today)

The implemented API is `/sprint/*`, `/health`, and `/v1/console/*`, defined in [src/sprint_crew/api/app.py](../../src/sprint_crew/api/app.py) and [src/sprint_crew/api/console/](../../src/sprint_crew/api/console/); FastAPI serves its own OpenAPI at `/docs` when the backend runs.

| File | Contents |
|------|----------|
| [chat-console-api.md](chat-console-api.md) | Human-readable console API: state machine, endpoints with JSON examples, clarify/confirm shapes, mapping to `/sprint/*` — Implemented (durable sessions, SSE timeline, run queue and cancel; model-generated clarify with a deterministic fallback; see its status section for limitations) |
| [chat-console.openapi.yaml](chat-console.openapi.yaml) | OpenAPI 3.1 spec aligned with the markdown; enough to generate a client |

Pydantic models matching these contracts live in `src/sprint_crew/schemas/console.py` (strict `extra="forbid"`, unit-tested).

## M0 frontend delta (regenerate client)

| Change | Kind | What the UI must do |
|--------|------|---------------------|
| Shared bearer auth | breaking | Send `Authorization: Bearer <CONSOLE_API_TOKEN>` on every `/v1/console/*` and `/sprint/*` call when the backend has the env set. `GET /health` stays open (no header). |
| `ConsoleSession.required` tightened | breaking (codegen) | Treat `confirmed`, `messages`, `clarify_questions`, `clarify_answers`, `created_at`, `updated_at` as always present (not optional). Nullable fields (`intent`, `sprint_ref`, `plan_result`, …) still may be `null`. |
| Create-with-prompt response | behavioural | After `POST /sessions` with `initial_prompt`, `status` is `clarifying` or `ready` — not stuck in `collecting`. |
| `SessionStatus` / `BacklogRunStatus` gain `cancelled` | additive | Allow `"cancelled"` when typing sprint/backlog poll responses. Emitted for real since M5. |
| Clarify fallback suggestion ids | fix | Stub path uses `s-scope-focused` / `s-scope-broad` (not `s-api`). Prefer driving off `suggestions[]` from the response, not hard-coded ids. |

## M5 frontend delta (run lifecycle)

| Change | Kind | What the UI must do |
|--------|------|---------------------|
| `POST /start` returns `202` | breaking | Accept `202`, not `200`. The run is queued, not finished — planning progress arrives on the event stream. Also applies to `POST /sprint/from-prompt` and `/from-ticket`. |
| New status `queued` + `queue_position` | additive | Render "waiting for the run slot, N ahead". A session may go straight from `ready` to `running`, so handle both. |
| `cancel_requested_at` | additive | While non-null and `status` is still `running`, show Stop as pending. It flips to `cancelled` when the run unwinds. |
| Cancel is asynchronous | behavioural | `POST /cancel` returns `200` in both cases; read the body, not the status code, to tell "cancelled now" from "stopping…". |
| New events | additive | `run_queued`, `run_started`, `workspace_ready`, `backlog_planned`, `cancel_requested`, `cancelled`. |
| Restart marks in-flight runs failed | behavioural | A `queued`/`running` session becomes `failed` with `interrupted by restart` after a backend restart. Nothing resumes. |

Backend env the UI operator must share: `CONSOLE_API_TOKEN` (same value in FE config), optional `CONSOLE_CORS_ORIGINS` listing the UI origin (not `*` in non-dev).

## How the UI repo consumes these

1. Generate or hand-write a client from [chat-console.openapi.yaml](chat-console.openapi.yaml); mock the server from its examples.
2. Attach the bearer header to the HTTP client when a token is configured (see M0 delta).
3. Follow the session flow from [chat-console-api.md](chat-console-api.md): create → messages → clarify → confirm → start; then read the timeline from `GET /v1/console/sessions/{id}/stream` (SSE) or `GET .../events?since=` (polling), and poll `GET /v1/console/sessions/{id}` for status, `queue_position`, and `cancel_requested_at`.
4. The timeline endpoints cover a whole run, so walking `sprint_ref` per ticket is optional; `GET /sprint/backlog/{run_id}` and `GET /sprint/session/{session_id}` remain available for scripts.
5. `/v1/console/*` is live: sessions are durable in SQLite, the timeline streams over SSE, one run executes at a time and Stop really stops. Clarify questions are model-generated by the Interpreter (ADR 0013), degrading to a deterministic fallback when the Work lane is cold; the current `/sprint/*` endpoints are stable aside from the shared auth gate and the `202` change.
